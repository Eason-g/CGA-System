# 非功能验证（P2 D 批）

对应 [P2设计.md](P2设计.md) 的 D 批：敏感信息加密（D.1）、登录防护与安全头（D.2）、性能与并发（D.3）、配置化扩展（D.4）。

## 1. 敏感信息加密（D.1）

| 项目 | 实现 |
|---|---|
| 加密算法 | AES-256-GCM，每次加密随机 12 字节 IV，128 位认证标签；库中格式 `enc:v1:<Base64(IV \| 密文 \| 标签)>` |
| 加密字段 | `users.phone`、`users.email`，实体字段上用 `crypto/EncryptedStringTypeHandler` 透明加解密 |
| 兼容明文 | 读取时不带 `enc:v1:` 前缀的值原样返回，所以迁移完成前、迁移过程中都能正常读 |
| 邮箱检索 | 新列 `users.email_hash` = HMAC-SHA256(去空格、转小写的邮箱)，64 位十六进制；邮箱登录改为 `email_hash = ?` 等值查询，不再查邮箱列本身 |
| 密钥 | `app.crypto.key`：Base64 编码的 32 字节。开发默认值写在 `application.yml` 并注明仅供开发；生产用环境变量 `APP_CRYPTO_KEY` 覆盖（`openssl rand -base64 32`） |
| 密钥校验 | 缺失、不是 Base64、解码后不是 32 字节时 `CryptoConfig` 抛出带原因的异常，应用启动失败 |
| 启动迁移 | `crypto/SensitiveDataMigrator`，由 `DatabaseInitializer` 在建表、重置演示数据和每次启动时调用，可以重复执行：老库自动补 `email_hash` 列和索引、加宽 email/phone 列、删掉明文邮箱索引；明文行加密；按解密后的邮箱重算哈希，与库里不同才更新。已是密文但解不开（密钥换了）时启动失败 |
| 改邮箱 | `ProfileService` 写邮箱时同步更新 `email_hash`；清空邮箱时哈希置空 |

**HMAC 密钥为什么由主密钥派生**：用 HKDF-SHA256（RFC 5869，salt=`cga-system`，info=`cga-email-hash-v1`）从 `app.crypto.key` 派生出 HMAC 密钥，而不是直接拿 AES 密钥去算 HMAC。

- 同一把密钥不同时用于两种算法，派生出来的两把密钥在密码学上相互独立，HMAC 值不会泄露 AES 密钥的任何信息；
- 运维只需要管理一个配置项，不会出现两把密钥只换了一把、或者生产环境漏配其中一把的情况；
- 代价是换主密钥时检索哈希也要跟着重算。启动迁移每次都会按当前密钥重算并修正 `email_hash`，所以这一步不用人工处理；但已加密的数据需要先用旧密钥解密（目前没有做在线换钥工具，见第 5 节）。
- 用带密钥的 HMAC 而不是普通 SHA-256：邮箱的取值空间很小，没有密钥的哈希可以靠字典枚举还原。

**明文不外泄的检查**：

- 快照：TypeHandler 读出时已经解密，`SnapshotService` 原有的打码逻辑不变（本人和校级管理员看明文，其他人打码，学生看不到别人的联系方式）；`emailHash` 字段 `@JsonIgnore`，不出现在任何响应里。
- 报表导出：5 种报表都没有手机号、邮箱列。测试会逐个导出 csv，检查里面没有邮箱、手机号（明文和打码形式都没有）和密文。
- 审计日志：改个人信息只记录"已更新联系方式与技能标签"，不记录具体值。测试改完邮箱、手机号后，用 SQL 在 `audit_log` 的 action/opinion/before_value/after_value 里搜新旧值，结果为 0 条。
- 合规核验列表（`ComplianceService`）对非本人同样打码，逻辑没有改动。

## 2. 登录防护与安全头（D.2）

| 规则 | 默认值（`app.security.login.*`） | 说明 |
|---|---|---|
| 账号锁定 | 15 分钟内连续失败 5 次 → 锁定 15 分钟 | 第 5 次失败直接返回 429 并提示"请 N 分钟后再试"，`data.retryAfterSeconds` 给出剩余秒数；锁定期间密码正确也返回 429；登录成功清零 |
| 锁定的计数单位 | 按用户计 | 用户名、学号、邮箱换着试算同一个账号；查无此人时按输入的账号字符串计，不存在的账号也会"锁定"，所以不能靠 429 和 401 的区别判断账号是否存在 |
| IP 限流 | 每个 IP 在任意连续 60 秒内最多 300 次登录请求（滑动窗口） | 超限时返回 429、`Retry-After` 头和 JSON。阈值按一个机房或宿舍楼 100 人左右共用一个校园网出口、在一两分钟内集中登录、每人输错一两次来估算；在线猜密码通常每分钟上千次，300 次足以让它失去意义 |
| 限流的接口 | `/api/auth/login`、`/api/auth/sso/exchange`（B 批的统一认证换票） | 通过 `ip-limited-paths` 配置。换票接口上线并设为公开访问后自动计入；其他登录入口加到这个列表里即可，也可以在代码里调用 `LoginGuard.checkIp` |

- 计数放在进程内（`ConcurrentHashMap` 加单 key 加锁），单实例部署够用，重启后清零；多实例部署需要换成 Redis。计数表变大时会顺带清理过期条目。
- IP 取 `remoteAddr`，不信任 `X-Forwarded-For`（和 P1 的评价限流一致）。
- 并发下的竞态：同一账号的 N 个错误密码请求如果同时到达，都会先通过"未锁定"检查，所以锁定前最多可能多试 N−1 次。每次失败本身的计数是精确的，单元测试里 999 个线程并发计数一次都没丢。

**安全响应头**（`security/SecurityHeaders`，由 `SecurityConfig` 的 `.headers(...)` 引用）：

| 响应头 | 值 |
|---|---|
| `X-Content-Type-Options` | `nosniff` |
| `X-Frame-Options` | `DENY`（本系统没有需要被嵌入的页面） |
| `Referrer-Policy` | `strict-origin-when-cross-origin`（跨站只带来源域名，不带路径和评价码等查询串） |
| `Content-Security-Policy`（接口） | `default-src 'self'; frame-ancestors 'none'; object-src 'none'; base-uri 'self'` |
| `Content-Security-Policy`（`/mock-cas/**`） | 在上面的基础上允许 `'unsafe-inline'` 脚本和样式、`data:` 图片，方便 B 批服务端输出的简单页面直接打开；同样禁止被嵌入。没有限制 `form-action`，因为登录后要 302 跳回前端地址 |

HSTS 沿用 Spring Security 的默认行为，只在 HTTPS 请求上输出。

## 3. 性能与并发（D.3）

### 3.1 测试环境

| 项目 | 配置 |
|---|---|
| CPU | Intel Core i7-13650HX（14 核 20 线程） |
| 内存 | 15.6 GB |
| 操作系统 | Windows 11 家庭中文版 23H2（10.0.22631） |
| 数据库 | MySQL 5.7.44（本机，`max_connections=151`），专用库 `cga_test_c` |
| 后端 | Java 25.0.1，Spring Boot 4.1.2，端口 8090，HikariCP `maximum-pool-size=20`，Tomcat 默认 200 个线程 |
| 压测客户端 | Node v24.12.0，`scripts/perf-test.mjs`，和后端在同一台机器上 |

压测客户端、后端、MySQL 在同一台机器上抢 CPU，所以结果偏保守。后端满载时 java 进程大约占 15 个逻辑核，还有一部分 CPU 被客户端和 MySQL 用掉。

启动命令：

```bash
cd server
SERVER_PORT=8090 mvn spring-boot:run -Dspring-boot.run.jvmArguments="\
  -Dspring.datasource.url=jdbc:mysql://localhost:3306/cga_test_c?useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai \
  -Dapp.db.init=always -Dapp.security.login.ip-max-per-minute=1000000 -Dapp.finance.mock.auto-callback=false"
# 另开一个终端，在仓库根目录：
node scripts/perf-test.mjs --base http://localhost:8090 --concurrency 50 --duration 60
node scripts/perf-test.mjs --base http://localhost:8090 --concurrency 200 --duration 60 --scenario login-snapshot
```

所有请求都来自 127.0.0.1，所以压测时把登录 IP 限流调高；否则 300 次/分钟的默认阈值很快会让登录返回 429。这正说明限流在生效，但不是这里要测的内容。

**场景**：

- `mixed`：准备阶段由导师建 4 个岗位（每个 1 个名额、8h/周），走完院系初审和国际生办会签后发布。之后每个虚拟用户循环按权重随机执行：登录 10、学生快照 25、导师快照 12、院系管理员快照 8、国际生办快照 5、校级管理员快照 8、学生投递 15、导师录用 10、院系管理员薪酬核算 7。录用时随机挑一个待选拔申请，因此会出现多个线程同时录用同一个学生、或者同时录用同一个岗位。
- `login-snapshot`：只执行登录和五种角色拉快照。

**结果分三类**：成功（2xx）；业务拒绝（400/403/404/409，例如重复投递、名额已满、超工时，这些都是预期内的规则拦截）；错误（401/429/5xx、网络错误、30 秒超时）。

### 3.3 并发录用不突破上限（压测后用 SQL 核对）

R2、R4 之后分别执行：

```sql
SELECT u.id, u.max_weekly_hours, SUM(c.weekly_hours) AS total_h, COUNT(*) AS n
FROM contracts c JOIN users u ON u.id = c.student_id
WHERE c.status IN ('ACTIVE', 'PENDING_SIGN') GROUP BY u.id, u.max_weekly_hours;

SELECT j.id, j.quota, COUNT(a.id) AS hired
FROM jobs j LEFT JOIN applications a ON a.job_id = j.id AND a.status = 'HIRED'
WHERE j.title LIKE '压测%' GROUP BY j.id, j.quota;
```

两次结果相同：4 名学生的生效和待签合同合计周工时分别是 20、20、18、16，都没有超过上限 20h；7 个压测岗位每个名额 1 个，录用人数都不超过 1。50 并发下有 3,623 次录用请求，其中包括多个线程同时录用同一学生到不同岗位、同时录用同一岗位的情况，最终只有 4 次成功。这里 SUM 把所有生效和待签合同加在一起，没有区分聘期是否重叠，比规则引擎"只计重叠聘期"更严，因此结果偏保守。

### 3.4 连接池（HikariCP）

`application.yml` 中的配置：`maximum-pool-size=20`、`minimum-idle=10`、`connection-timeout=5s`、`idle-timeout=10min`、`max-lifetime=30min`、`leak-detection-threshold=30s`。

对比测试（同一台机器，新建的演示库，200 并发"登录 + 快照"，60 秒）：

| 连接池大小 | 吞吐 | 错误 | 登录 p95 | 快照 p95（各角色） |
|---|---:|---:|---:|---:|
| 20 | 524.5 req/s | 0 | 776 | 483–618 |
| 40 | 523.3 req/s | 0 | 807 | 523–1220 |

两者吞吐相同，说明瓶颈不在等连接。压测时 java 进程约占 15 个逻辑核，线程转储里最常见的是 BCrypt 计算（每次登录约 50–70 ms CPU）和结果集映射。连接池开到 40 时导师快照的 p95 反而变长，推测是 MySQL 里同时执行的查询变多、互相争 CPU，但没有进一步验证。所以保持 20：

- 本机 20 个逻辑核，20 个连接已经足够让 CPU 跑满；
- 写接口有 `SELECT … FOR UPDATE` 行锁，同一行上的事务只能排队，多给连接只会让更多事务在 MySQL 里等锁；
- 远低于 MySQL 默认 `max_connections=151`，给开发库、测试库和运维连接留出余量；
- 等连接超过 5 秒就快速失败（返回 500），说明已经严重过载，比让请求无限排队更容易发现问题；`max-lifetime` 30 分钟，远小于 MySQL `wait_timeout`（默认 8 小时），不会拿到已经被服务端断开的连接。

### 3.5 发现的问题：快照随审计日志增长变慢

R1 和 R3 的接口、并发、时长都相同，吞吐却从 531.6 降到 322.2 req/s。区别在于 R2 期间院系管理员执行了 2,427 次薪酬核算，每次都写一条批量核算审计日志，`audit_log` 从十几条增长到约 2,460 条。校级和院系管理员的快照会返回范围内的全部审计日志，响应体从约 36 KB 增长到约 650 KB，序列化开销挤占了 CPU，所有接口都跟着变慢（R3 的 p95 仍 ≤ 1.2 s，没有错误）。

现实中薪酬核算每月只做几次，这样的增长速度是压测人为造成的；但长期运行后审计日志会持续增加，快照返回全部日志的做法迟早会成为瓶颈。目前没有改动，原因是前端审计页、归档页、详情抽屉都直接读 `store.db.auditLogs`。建议后续让审计日志走单独的分页接口（`GET /api/audit-logs?targetType=&targetId=&page=`），快照里只保留最近若干条。

非功能参数包括：加密密钥 `app.crypto.key`；登录防护 `app.security.login.*`；评价限流 `app.feedback.rate-limit.*`；连接池 `spring.datasource.hikari.*`；财务回调密钥与模拟网关 `app.finance.*`；演示日期 `app.today`、学期起始日 `app.semester-start`；上传目录 `app.upload-dir`；CORS 白名单 `app.cors.allowed-origins`。

### 4.2 新增一种外部系统实现的步骤

外部系统一律采用"接口 + 实现"的写法：业务代码只依赖接口，现有的模拟实现读 `server/src/main/resources/integration/*.json`（P1 的财务网关是 `FinanceGateway` / `MockFinanceGateway`；P2 B、C 批是 `SsoProvider`、`SisGateway`、`ResearchGateway`、`TeachingEvalGateway`）。以接入真实的学籍系统为例：

1. **新建实现类**，例如 `integration/sis/HttpSisGateway implements SisGateway`，负责调用对方接口、把返回值转换成接口里定义的对象，并把对方的错误统一转换成 `BizException`（对方不可用时返回 502 或 503 并提示"学籍系统暂不可用"，不能把异常栈返回给前端）。
2. **用配置选择实现**：在新类上加 `@ConditionalOnProperty(prefix = "app.sis", name = "provider", havingValue = "http")`，模拟实现加 `@ConditionalOnProperty(..., havingValue = "mock", matchIfMissing = true)`，保证任何时候只有一个实现被注册，不配置时默认用模拟实现。P1 的 `MockFinanceGateway` 目前还是无条件注册的 `@Component`，接入真实财务系统时要先给它加上这个条件。
3. **连接参数放到配置里**：在 `application.yml` 中增加 `app.sis.http.base-url`、超时等参数，并写中文注释；访问密钥和签名密钥一律用 `${APP_SIS_SECRET:}` 这类环境变量注入，缺失时像 `CryptoConfig` 一样启动失败，不在代码和仓库里保存。
4. **安全**：对方回调本系统时，参照财务回调：`SecurityConfig` 只放行这个回调路径，入口用 HMAC 校验签名，按流水号保证幂等；本系统主动调用对方时设置连接超时和读超时（建议 3 s / 10 s），并按 IP 白名单或双向 TLS 限制来源。
5. **数据同步与留痕**：同步类接口返回差异清单并写审计日志；涉及手机号、邮箱这类敏感字段时，用实体字段赋值，经过 `EncryptedStringTypeHandler` 加密落库，不要用 JdbcTemplate 直接写明文。
6. **测试**：保留模拟实现作为集成测试的默认实现；给新实现写单元测试，用本地 HTTP 桩或 MockRestServiceServer 模拟对方返回，覆盖成功、对方报错、超时、签名错误几种情况；测试配置里不切换 provider，避免集成测试依赖外部网络。
7. **切换上线**：生产环境设置 `APP_SIS_PROVIDER=http`（对应 `app.sis.provider`）和相关密钥，重启生效；回退时把它改回 `mock` 即可。界面上标注"模拟"的文案由各批的配置项控制，切换到真实实现后应该去掉。

## 5. 已知局限

- 登录锁定和 IP 限流的计数在进程内，多实例部署时需要换成 Redis 等共享存储，重启后计数清零。
- 没有在线换钥工具：更换 `app.crypto.key` 之前需要先用旧密钥解密全部数据（或者增加 `enc:v2:` 前缀、按版本选择密钥），否则启动迁移会因为解不开密文而失败。目前只保证不会带着错误的密钥继续写入数据。
- 只加密了手机号和邮箱。签证号等字段目前库里没有存储；以后增加时，在实体字段上加 `EncryptedStringTypeHandler`，再把列名加进迁移器即可。
- 压测客户端和后端在同一台机器上，数值偏保守；快照随审计日志增长变慢的问题见 3.5。
